How GPU matmul got asynchronous

The last five years of NVIDIA's data-center GPUs can be told as a sequence of overlap problems, each generation killing the bottleneck the previous one made visible. Pre-Ampere was synchronous. Ampere unlocked in-CTA pipelining. Hopper unlocked cross-tile pipelining. Blackwell unlocked a three-stage pipeline that bypasses the register file. The pattern is so consistent it's worth tracing on purpose.

There is a particular flavour of progress that GPU architecture follows which is harder to see if you're reading whitepapers one generation at a time but obvious if you line them up next to each other: each generation of NVIDIA Tensor Core hardware quietly removes one source of serialization, and then the next generation goes to work on what that exposes.

Each generation kills the latency the last one made visible.

This post walks through that progression for matrix-multiply kernels — the workload that most of NVIDIA's data-center engineering decisions are made in service of — starting from the Volta / Turing era of synchronous instruction streams and ending at Blackwell's three-stage pipeline backed by dedicated tensor memory.

01 Pre-Ampere: when memory blocked compute

Before cp.async, memory loads and arithmetic ran on the same in-order instruction stream from each warp's perspective. A thread that issued a global-memory load through the L1 / L2 path simply waited until the data arrived in registers before it could do anything else with it. From inside a single CTA, the timeline of a matmul tile looked like this: 

// single CTA · synchronous · serial within itself
CTA0 │ ──[Load A]──[Wait]──[Load B]──[Wait]──[Compute]──[Wait]──[Store]──

The standard workaround was to lean on the SM's warp scheduler. If you sized each CTA small enough that the SM could host two, three, four of them at once, the scheduler would happily issue instructions from a different CTA while the first was stalled on a load. From the SM's point of view, that looked like: 

// multi-CTA · SM-level overlap, sometimes called "double buffering"
CTA0 │ ──[Load]──[Wait]────[Compute]────[Store]──
CTA1 │     ──[Load]──[Wait]────[Compute]────[Store]──
CTA2 │         ──[Load]──[Wait]────[Compute]────[Store]──
       └──── overlap comes from CTA-to-CTA scheduling ────┘

This worked. It also paid for itself in two awkward ways:

  • Smaller tiles per CTA. An SM has a fixed budget of registers and shared memory. To fit several CTAs concurrently you had to slice each one into a smaller tile — which meant more total kernel launches, more index arithmetic, and less amortization of the MMA pipeline you were trying to keep fed.
  • Forced trade-off between occupancy and resources. If a kernel wanted the biggest possible tile (good for arithmetic intensity), you'd end up with one CTA per SM and no warp-scheduler-based overlap at all. Picking a tile size was as much about occupancy gymnastics as about the math itself.

So pre-Ampere kernels were a constant negotiation between three constraints — tile size, register pressure, occupancy — none of which had anything to do with the matrix multiplication itself. Removing that negotiation is what Ampere set out to do.

02 Ampere: cp.async and in-CTA pipelining

Ampere's headline addition for matmul wasn't a faster Tensor Core; it was the cp.async instruction. The semantics are simple but the consequences are not: a thread can issue a global → shared memory copy and immediately continue executing without blocking on the load. The hardware tracks the in-flight copy with a per-thread async-copy pipeline; you fence on it with cp.async.wait_group when you actually need the data. 

// PTX-flavoured pseudocode for a software-pipelined matmul iter
cp.async.cg.shared.global   [smem_A + (k+1)*stride], [gmem_A + (k+1)*stride], 16;
cp.async.cg.shared.global   [smem_B + (k+1)*stride], [gmem_B + (k+1)*stride], 16;
cp.async.commit_group;       // snapshot the in-flight copies

mma.sync.aligned.m16n8k16   d, a[k], b[k], c;   // compute stage k on already-loaded data

cp.async.wait_group 1;       // before next iter, ensure k+1's load has landed
__syncthreads();

With this primitive, a single CTA can now run its own software pipeline: issue the load for tile k+1, do the MMA for tile k, store the result for tile k–1, all in flight at once. 

// single CTA · in-kernel software pipeline (Ampere)
CTA0 │ ─[Load k]──[Load k+1]──[Load k+2]─────────
     │         ─[MMA  k  ]──[MMA  k+1]──[MMA k+2]
     │                   ─[Store k–1 ]──[Store k ]─

The win is bigger than just hiding latency. Because overlap is now happening inside the CTA, you no longer need to slice tiles small enough to fit several CTAs on an SM. One large CTA per SM — using all the registers and all the shared memory — is now the productive choice. The occupancy gymnastics of the previous section dissolves into a straightforward double- or triple-buffered loop.

What Ampere did not fix is the rest of the per-tile bookkeeping: every CTA still launches from the host, every CTA still computes its own block indices and prologue, and every CTA still terminates after its tile. On A100 the kernel launch + setup overhead is single-digit microseconds, which is fine if your tiles are big but ruinous when they aren't. That bill is what Hopper picked up.

03 Hopper: TMA, WGMMA, and the persistent kernel

Hopper's tensor-core story is built on three additions that compose cleanly: the Tensor Memory Accelerator for asynchronous tile movement, asynchronous warpgroup MMA for issuing compute that doesn't block the warp, and the persistent kernel programming model that the first two make possible.

TMA: hardware that moves tiles, not threads

On Ampere, even cp.async is a per-thread operation: each thread computes the address it's responsible for and issues its own copy. For a matmul tile, that's a lot of cooperative address arithmetic with a lot of edge cases (swizzling, padding, boundary tiles). TMA replaces all of that with a single instruction issued by a single thread that describes a tile in terms of a tensor descriptor — origin, shape, stride — and asks the hardware to move it asynchronously from global to shared memory.

The address arithmetic, vectorization, and swizzling all happen in a dedicated hardware unit. From the kernel's perspective you set up the descriptor once, issue a copy, and synchronize on an mbarrier when you need the data. The thread that issues the copy doesn't even need to be in the warp that will eventually consume it.

WGMMA: MMA that doesn't block its warp

Ampere's mma.sync instruction is synchronous — when you issue it, the warp blocks until the MMA is done and the result is in registers. Hopper introduces wgmma.mma_async ("warpgroup MMA"), which is issued by a four-warp group, executes asynchronously on the Tensor Cores, and lets the issuing warps continue executing other instructions while the MMA is in flight. You fence on the result with wgmma.wait_group when you actually need it.

The combination of TMA and WGMMA is what makes overlap inside a Hopper kernel feel categorically different from Ampere. On Ampere you could overlap a memory copy with a compute instruction. On Hopper you can overlap a memory copy, multiple in-flight MMAs, and the address arithmetic of the next iteration, all on the same warpgroup, with the hardware doing the bookkeeping.

Persistent kernels: stop relaunching

Once you can keep arbitrary work in flight inside a CTA, the natural next move is to stop ending the CTA at all. A persistent kernel is a matmul kernel where each CTA launches once, claims a stream of tiles from a global counter, and processes them one after another without returning to the host. The launch overhead is paid once for the whole problem instead of once per tile, and — more importantly — the boundary between one tile and the next becomes a place where you can pipeline. 

// persistent CTA · cross-tile pipelining (Hopper)
CTA stays resident on the SM, processing tiles N–1, N, N+1, …

  TMA store ─┐
  tile N–1   │
             ├──┐
  WGMMA      │  │ Tensor cores ─┐
  tile N     │  │  computing    │
             │  │               ├──┐
  TMA load   │  │               │  │
  tile N+1   ┘  ┘  ──→ in flight together ──→

On Hopper, that picture is real: the output of one tile being written back to global memory, the MMA of the next tile running on Tensor Cores, and the TMA for the tile after that streaming in from HBM — all running concurrently inside a CTA that never went home.

The catch is that WGMMA consumers use a lot of registers. Each warpgroup asking for a big accumulator tile is asking for hundreds of registers per thread to hold partial sums, and those registers come out of the same SM budget that occupancy, async barriers, and the rest of the program all have to share. Worse, the Tensor Cores and the ALU paths inside the SM compete for issue slots: a kernel that wants to do a lot of epilogue work (elementwise scaling, bias add, activation, quantization) in registers starts trading off MMA throughput against the same resources. That tension is what Blackwell goes after.

04 Blackwell: tensor memory and a true three-stage pipeline

The Blackwell architecture introduces a new MMA family — exposed in PTX as tcgen05.mma — whose accumulator does not live in registers at all. Instead, results go into a dedicated on-chip pool called tensor memory, sized and scheduled independently of the register file. Stores back to global memory read from tensor memory directly.

On Blackwell, the accumulator gets its own pool of silicon. Registers stop being the bottleneck nobody talks about.

The consequence is that the three things a matmul kernel does — load, compute, store — now live on three independent memory regions and can be in flight on three independent tiles at the same time: 

// persistent CTA · three-stage pipeline (Blackwell)

  stage A · TMA load            tile N+1   ──→ shared memory
  stage B · tcgen05 compute     tile N     ──→ tensor memory
  stage C · async store         tile N–1   ──→ global memory

                ↑ three different memory regions, three different tiles ↑
                       in flight concurrently inside one CTA

Each stage runs on its own hardware: TMA engines on the load side, Tensor Cores into tensor memory in the middle, and async copies from tensor memory on the store side.

Two things change in practice. First, accumulator size stops competing with register pressure: a kernel that wants 256×256 accumulators no longer pays for it by losing occupancy. Second, the epilogue can run on the integer / FP32 ALU paths in parallel with the Tensor Cores, because the accumulator doesn't need to be staged through registers to be operated on. The bias add, the scale, the quantization can fuse into the store stage without stealing issue slots from the next MMA.

The result is the cleanest software pipeline NVIDIA has shipped: three stages, three hardware units, three tiles, all overlapped, all running inside a single persistent CTA that paid its launch cost once at the start of the problem.

05 The pattern, restated

Put the four architectures next to each other and the pattern becomes impossible to miss:

Gen What it added What it fixed What it left exposed
Pre-Ampere (baseline) — Memory blocks compute; multi-CTA workaround forces small tiles
Ampere cp.async In-CTA overlap of loads and MMA Per-tile launch + setup overhead
Hopper TMA, WGMMA, persistent kernels Cross-tile overlap; launch cost amortized Register pressure from WGMMA; Tensor Core ↔ ALU issue contention
Blackwell tcgen05 + tensor memory Accumulator off the register file; clean three-stage pipeline ?

Every generation's "fixed" column is the previous generation's "left exposed" column. That isn't a coincidence — the way you make a real workload faster is to find the longest pole and shorten it, and on a matmul-shaped workload the longest pole has migrated, neatly, from memory-blocking-compute to launch overhead to register pressure to whatever the next one turns out to be.

06 Where the bottleneck moves next

With the three big in-kernel constraints resolved — synchronous memory, relaunch cost, register-bound accumulators — the interesting candidates for the next bottleneck have moved out of the SM:

  • Cross-CTA / cross-SM communication. Now that a single CTA can saturate its Tensor Cores, the next gain comes from making cooperating CTAs share data and reductions without going back through HBM. Hopper's distributed shared memory (the SM-to-SM "thread block cluster") is the first move in this direction; it's not hard to imagine that becoming the central abstraction rather than a side feature.
  • Instruction issue. When the hardware units are independent and the data is staged, the scheduler choosing which instruction to issue next becomes a real cost. Persistent kernels with three-stage pipelines already push hard on the front end; future workloads (more epilogue fusion, more attention variants, more sparsity) push harder.
  • Off-chip bandwidth and topology. NVLink Switch, NVL72, GB200 — at cluster scale the bottleneck stops being inside the SM at all and starts being whether the system can keep the GPUs fed. The matmul kernel is asynchronous; now the rest of the stack has to catch up.

None of these is a guess at what Blackwell-Ultra or Rubin will actually add. The point is narrower: the pattern of "find the longest pole, kill it, ship the next architecture" has been remarkably consistent for half a decade of NVIDIA silicon, and the longest poles that remain are no longer inside the SM. That's a useful thing to know if you're deciding what kind of kernel to optimize this quarter.
